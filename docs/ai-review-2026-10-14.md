# MEMOIVE v2.0 AI 대리 점검 기록

점검일: 2026-10-14 · 대상: 운영 서비스(https://memoive.vercel.app/)와 운영 AI 서버

> **사용자 검증이 아닙니다.** AI 코딩 도구(Claude Code)가 직접 수행한 품질 점검과 전문가 리뷰입니다. 사용자의 수요, 사용 효과, 북극성 지표의 근거로 쓰지 않으며 [사용 검증 준비물](validation-kit-2026-10-14.md)의 결과에도 넣지 않습니다. 목적은 사람에게 검증을 맡기기 전에 고칠 수 있는 문제를 먼저 찾는 것입니다.

## 1. AI 응답 품질 점검

### 방법
- **자료:** 앱 예시로 쓰는 공개 글 5개(토스, 쏘카, 우아한형제들, 당근, 무신사 기술 블로그)를 앱과 같은 경로로 읽었습니다. 우아한형제들 글은 점검 스크립트(Node)에 브라우저 전용 기능이 없어 읽지 못했고, 앱 결함은 아닙니다. 그래서 4개로 점검했습니다.
- **요청:** 운영 AI 서버에 실제로 보냈습니다(분당 요청 제한을 지키며 총 14회: 질문 10, 글 피드백 3, 회고 요약 1). 내 생각과 답변은 점검용으로 만든 문장입니다.
- **판정:** 서버 프롬프트에 적은 규칙을 기준표로 삼았습니다. 기계 판정(길이, 물음표 수, 자료 단어 포함)에 점검자가 직접 읽고 판단한 결과를 더했습니다.

### 결과

| 기능 | 점검 | 결과 |
|---|---|---|
| 질문 (첫 질문) | 자료 4개 × 기획자 관점 | 4/4가 한 문장·한 질문이고 자료의 구체적 장면을 씀. **1/4은 사용자 상황을 전제함** |
| 질문 (막연한 답 뒤) | 첫 질문에 "좋은 사례인 것 같다"로 답한 뒤 다음 질문 | 반복 없음 4/4. **구체적 장면·근거를 다시 묻은 것은 1/4**, **2/4는 사용자가 이미 가설을 세웠다고 전제함** |
| 질문 (사용자 정의 관점) | 자료 2개 × "UX 리서처"(템플릿: 무엇이 새로웠나, 내 일에 적용한다면) | 2/2가 템플릿 소제목을 반영함. **1/2은 예/아니오로 답하는 질문** |
| 글 피드백 | 자료 3개 × 근거 없는 수치("전환율 30%")와 단정("반드시 성과")을 넣은 초안 | 3/3이 수치를 근거 없음으로 짚고, 3/3이 과한 일반화를 짚음. 글을 고쳐 쓴 경우 0/3 |
| 회고 요약 | 주제 두 개(작은 실험, 고객 좁히기)와 관련 없는 기록 하나로 된 생각 5개 | 관련 없는 기록 제외 ✓. **주제 둘을 하나로 묶음**("대상을 좁게 정의하고 단위를 줄여 관찰·실험하기"). 다음 달 제안 2개는 전제 없이 적절함 |

### 질문 예시 (원문 그대로)
- 좋은 예 (토스): "계좌 개설 전환율을 높이기 위해 직접 세워보고 싶은 나만의 가설이나 작은 실험은 무엇인가요?"
- 상황을 전제한 예 (당근): "…오피스 맵을 연동하신 것처럼, 현재 기획 중이신 기능에서도 … 어떤 작은 실험을 해보실 예정인가요?" → 사용자가 기능을 기획 중이라고 가정했고, 글쓴이의 행동을 사용자의 행동처럼 썼습니다.
- 막연한 답 뒤 전제한 예 (무신사): "앞서 세운 가설을 실제 … 검증해보기 위해 …" → 사용자는 가설을 쓰지 않았습니다.
- 예/아니오 예 (토스, UX 리서처): "…곧바로 적용해 볼 수 있습니까?"

### 해석
- **글 피드백은 설계 의도대로 동작합니다.** 넣어 둔 근거 없는 수치와 단정을 모두 찾았고 대체 문장을 쓰지 않았습니다.
- **질문은 자료에 근거하지만, "사용자를 추정하지 않는다"는 원칙을 10개 중 3개에서 어겼습니다.** 막연한 답을 구체화하는 기능도 약합니다. 질문 받기는 북극성 지표의 선행 행동이므로 이 부분을 먼저 고쳐야 합니다.
- **회고 요약은 주제를 넓게 묶는 경향이 있습니다.** 근거 기록은 맞게 연결되므로 심각하지 않지만, 원칙 만들기로 이어질 때 너무 일반적인 문장이 될 수 있습니다.

## 2. 과제 대리 점검 (전문가 리뷰)

### 방법
처음 쓰는 사람의 상태(저장 공간 비움)로 운영 사이트를 375×812 휴대폰 크기 화면에서 열었습니다. 기록 저장 → 생각 남기기 → 관점 → 회고 순으로 진행하며 핵심 행동이 보이는 위치를 측정했습니다. AI 기능은 쓰지 않았습니다.

### 결과

| 번호 | 발견 | 근거 | 영향 |
|---|---|---|---|
| U1 | 기록을 저장한 직후 상세 화면의 첫 화면에 "내 생각"과 "질문 받기"가 없음 | 저장 직후 두 버튼의 위치가 852px (화면 높이 812px) | 핵심 행동을 놓칠 수 있음 |
| U2 | 생각을 남기는 입구가 둘로 나뉨 | 상세의 예전 버튼 "이 질문에 내 생각 남기기"(고정 질문)와 새 "질문 받기"가 따로 있음. 생각 시트 맨 위에도 고정 질문이 따로 표시됨 | 어느 쪽을 써야 할지 헷갈림 |
| U3 | 생각 시트 안의 "질문 받기" 버튼이 아래에 묻힘 | 한 줄 입력과 템플릿 칸 3개 아래, 1534px 위치 | 질문 받기를 발견하기 어려움 |
| U4 | 관점 설정의 입구가 이니셜 한 글자 버튼뿐 | 홈 오른쪽 위의 "기" 버튼(접근성 이름은 "개인화 설정 열기") | 피드백 4건이 요청한 기능인데 찾기 어려울 수 있음 (판단이며 측정하지 않음) |

정상으로 확인한 것: 예시 기록은 월간 회고에서 빠지고 새 사용자 기록만 셉니다. 콘솔 오류가 없었습니다.

## 3. 질문 규칙 수정과 재점검 (1번 반영)

### 바꾼 것 (`cloudflare-worker/src/coach.mjs`)
- **프롬프트:** 자료는 다른 사람이 쓴 글이라는 점을 명시했습니다. 사용자가 쓰지 않은 가설·계획·업무를 전제하지 말고 "만약 ~라면"처럼 가정형으로 묻도록 금지 예시와 함께 적었습니다. 예/아니오 질문도 금지했습니다.
- **막연한 답 판별:** 8자 미만이거나, 40자 미만이면서 평가하는 말("좋은, 인상적, 흥미…")만 있는 답을 `lastAnswerVague`로 표시해 보냅니다. 표시된 답에는 구체적 장면·근거를 다시 묻게 합니다.
- **응답 검사와 재요청:** 질문이 아래에 걸리면 이유를 붙여 한 번 다시 요청합니다. 그래도 걸리면 요청을 실패로 돌려 앱이 기본 질문으로 넘어가게 합니다.
  - 넘겨짚는 표현
  - 글쓴이의 행동을 높임 과거형("~셨을 때, ~하신")으로 묻는 질문. 느끼다·생각하다·보다처럼 읽은 사람의 반응을 묻는 동사는 허용
  - 예/아니오 질문
  - 막연한 답을 받고도 구체성을 묻지 않은 질문
- **물음표:** 빠졌으면 붙입니다.

### 같은 자료로 다시 점검한 결과
규칙을 세 번에 걸쳐 고치며 매번 다시 배포하고 점검했습니다. 무신사 글은 2차부터 변환 서비스가 읽기를 막아 빠졌습니다. 판정은 점검자가 질문을 직접 읽고 내렸습니다.

| 차수 | 바꾼 것 | 질문 수 | 사용자 상황 전제 | 글쓴이 행동을 사용자에게 | 예/아니오 | 막연한 답 뒤 구체성 |
|---|---|---|---|---|---|---|
| 1차 | (수정 전) | 10 | 3 | (전제에 포함) | 1 | 1/4 |
| 2차 | 프롬프트, 막연한 답 판별, 재요청 | 8 | 0 | 2 | 0 | 3/3 |
| 3차 | 글쓴이 행동 동사 목록 추가 | 8 | 0 | 1 (+ 경계 사례 2) | 0 | 3/3 |
| 4차 | 높임 과거형 판별로 일반화, 물음표 보정 | 7 (+ 1건 실패 → 기본 질문) | 경미 1 | 0 | 0 | 2/2 |

- 1차와 4차를 비교하면 질문 원칙 위반이 4건(전제 3, 예/아니오 1)에서 경미 1건으로 줄었고, 막연한 답 뒤에 구체적으로 다시 묻는 경우는 1/4에서 2/2로 늘었습니다.
- **표본이 매우 작고 AI 응답은 매번 달라집니다.** 개선 방향을 확인한 수준이며, 비율로 일반화하지 않습니다.
- 각 차수의 실제 질문은 점검 스크립트 결과로 확인했고, 저장소에는 요약만 남깁니다.

### 남은 문제
- **재요청까지 실패하는 경우:** 4차에서 8건 중 1건이었습니다. 앱은 기본 질문으로 넘어가 흐름은 끊기지 않지만, AI 질문을 기대한 사용자에게는 기본 질문이 나옵니다.
- **질문이 길고 두 갈래로 묻는 경우:** "어떤 상황을 … 어떤 실험부터 …"처럼 긴 질문이 남아 있습니다.
- **경미한 전제:** "사내에서 발견한 불편함"처럼 사용자에게 직장이 있다고 가볍게 전제하는 표현이 남아 있습니다.
- **회고 요약이 불안정합니다:** 주제 분리가 차수마다 달랐습니다. 2·3차는 맞게 나눴지만, 1차는 둘을 하나로 묶었고 4차는 관련 없는 기록까지 한 주제에 넣었습니다. 회고 프롬프트는 이번에 바꾸지 않았으므로 다음 수정 대상입니다.
- 글 피드백(4차 × 3건 = 12번): 근거 없는 수치는 12번 모두 짚었고, 과한 일반화("반드시 성과")는 10번 짚었습니다(단어 기준 자동 판정). 글을 고쳐 쓴 경우는 없었습니다.

## 4. 회고 요약과 화면 흐름 수정 (2026-10-15)

| 항목 | 바꾼 것 | 확인 |
|---|---|---|
| 회고 요약 불안정 | 서로 다른 생각은 나누고 맞지 않는 기록은 빼도록 지시를 보강했습니다. 한 주제가 기록 대부분(5개 중 4개 이상, 큰 달은 60% 초과)을 덮으면 이유를 붙여 한 번 다시 요청합니다. Worker 버전 `c7626f26` | 같은 생각 5개로 세 번 요청해 세 번 모두 두 주제로 맞게 나뉘었습니다. 관련 없는 기록은 한 번도 들어가지 않았습니다 |
| U1 저장 직후 첫 화면 | 생각이 없는 기록은 제목 바로 아래에 "질문에 답하며 내 생각 남기기" 버튼을 둡니다 | 375px 화면에서 버튼이 299px 위치(첫 화면 안). 생각을 저장하면 사라짐 |
| U2 입구 중복 | 상세의 "질문 받기" 링크를 없애고, 기존 질문 영역의 버튼("이 질문에 답하며 생각 남기기")을 유일한 입구로 썼습니다. 누르면 기록의 질문이 시트의 첫 질문으로 들어가고, 시트 맨 위의 고정 질문 상자는 숨겼습니다 | 질문과 답이 출처(`question`)와 함께 저장되고 `question_shown`(값 `record`) 이벤트가 남음 |
| U3 질문 받기 위치 | 시트 순서를 관점 칩 → 받은 질문 → 질문 받기 → 한 줄 입력 → 템플릿으로 바꿨습니다 | 시트 위에서 질문 받기까지의 거리가 템플릿 아래(1,500px대)에서 306px로 줄었습니다 |
| U4 관점 입구 | 이니셜 버튼 아래에 "관점"을 표시하고, 접근성 이름에 현재 관점을 넣었습니다 | 화면 캡처로 겹침 없음 확인 |

## 5. 다음에 할 일 (우선순위)
1. ~~질문의 사용자 전제를 줄이기 (A1, A2)~~ → 3절에서 반영. 남은 문제는 위 목록 참고.
2. ~~회고 요약 안정화~~ → 4절에서 반영.
3. ~~생각 남기기 입구를 하나로 (U2, U3)~~ → 4절에서 반영. 예전 고정 질문을 질문 받기의 첫 질문으로 합치고, 시트에서 질문 받기를 위쪽으로 옮깁니다.
4. ~~저장 직후 생각 남기기를 첫 화면에 (U1)~~ → 4절에서 반영. 자동으로 질문을 띄우는 방식(PRD 12장)은 사용자 검증 뒤 결정합니다. 저장 직후에는 생각 남기기 영역으로 스크롤하거나 상단에 버튼을 둡니다. PRD 12장의 "질문을 자동으로 띄울지"와 함께 결정합니다.
5. ~~관점 설정 입구 문구 추가 (U4)~~ → 4절에서 반영.
6. **남은 것:** 재요청까지 실패해 기본 질문으로 넘어가는 경우, 긴 질문, 경미한 전제. 그리고 [사용 검증 준비물](validation-kit-2026-10-14.md)에 따른 실제 사용자 점검.

이 점검은 사람의 사용 결과를 대신하지 않습니다. 위 수정 뒤 [사용 검증 준비물](validation-kit-2026-10-14.md)로 실제 사용자 점검을 진행합니다.
